# First send with the Nitrosend CLI — report

- Install: `npm install @nitrosend/cli@0.3.9` into `/home/asd/nitro`; Node.js v26.7.0, npm 11.19.0, CLI 0.3.9 (`nitrosend --version` → `0.3.9`), Linux x64.
- Signup and sender: `nitrosend signup --email <me> --password-stdin` → account 13078 (created 19:20:29Z). Brand Kit complete; sender `hello@ilya-web-development.nitrosend.net`, `from_email_domain_status: verified`.
- Command that sent: `nitrosend send --to proof@dogfood.nitrosend.net --subject "First send via the Nitrosend CLI" --body "Hello from the Nitrosend CLI. This is a single transactional proof-of-work send." --idempotency-key cli-first-send-001` → exit 0, message id 5161538, `status: sent`, `sent_at 2026-10-21T19:24:36.768Z`, provider id `010001a15fec2f63-9fb4bf04-c5b9-4db1-93bc-e187f4565bcb-000000`.
- Minutes from install to first send: 125.7 (CLI installed 17:18:54Z, sent 19:24:36Z). 4.1 minutes from account creation to the successful send. The long middle was account screening, not CLI work.
- Slowest step: signup screening. Five earlier accounts (13064, 13065, 13072, 13073, 13076) were auto-held with `sending_paused` (`occurred_at` = `created_at` to the second) — 13064/13072/13073/13076 from REST or CLI signups on one mail domain, 13065 from a browser signup on a second — so both `prepare_sending` and `send` returned 422/65 `Sending is paused for this account`. The account that worked was the sixth. Nothing in the CLI docs says a signup can be held or how long it lasts; I only learned it from the API response.
- Doc gap, exact repro: `nitrosend send --to neutral-probe@example.com --subject t --body t --dry-run` prints `Valid: true` and exits 0, while the identical command without `--dry-run` exits 65 `Sending is paused for this account`. `--dry-run` is documented as "Validate without side effects" (CLI reference), so a client-side validation is what it promises — but the CLI never states that admission is decided server-side, so `Valid: true` reads as "this will send". `GET /v1/my/delivery/status` returns `admission_status: "denied"`, `blocking_control: "account_status"`, `retryable: false` and a `recovery_actions` link; none of that reaches the user.
- One change I would make: have `--dry-run` call `GET /v1/my/delivery/status` and print `admission_status` and `sending_pause` next to `Valid: true`, and include the server's `occurred_at` and `retryable` flags in the send error, which the CLI currently drops.
